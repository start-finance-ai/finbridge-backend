# FINANCE AI — MVP Scope

Last Updated: 2026-08-28

이 문서는 2026 금융 AI Challenge 예선 제출용 웹서비스의
목표 MVP 범위를 관리한다.

주의:

이 문서의 MUST는 현재 개발 목표이다.

최종 기능명세서에는 실제 구현 및 검증 완료된 기능만 작성한다.

구현되지 않은 기능을 제출 문서나 UI에서
구현된 기능처럼 표현하지 않는다.


# 1. MVP Goal

심사자가 Public URL에 접속한 뒤

사용자 상황 입력

→ 관련 지원사업 탐색

→ 매칭 근거 확인

→ 재무·창업 리스크 계산

→ AI 설명

→ 출처 및 다음 행동 확인

까지 하나의 사용자 시나리오로 직접 경험할 수 있도록 한다.


# 2. Primary Demo Scenario

MVP의 대표 시나리오는 다음과 같다.

1. 사용자가 자신의 유형을 선택한다.

   - 예비창업자
   - 소상공인
   - 프리랜서

2. 기본 프로필을 입력한다.

   예:

   - 지역
   - 업종
   - 자본금
   - 사용자 유형별 추가 조건

3. Backend가 실제 확보된 지원사업 데이터에서
   사용자 조건과 관련 있는 후보를 검색한다.

4. 서비스가 각 지원사업에 대해

   - 어떤 조건이 일치하는지
   - 어떤 조건은 추가 확인이 필요한지
   - 출처가 무엇인지

   보여준다.

5. 사용자가 재무·창업 관련 값을 입력한다.

6. Backend Calculation Engine이
   사전에 정의된 계산식에 따라 리스크를 계산한다.

7. 생성형 AI가

   - 검색된 지원사업
   - 사용자 프로필
   - 계산 결과
   - Evidence

   를 바탕으로 결과를 이해하기 쉽게 설명한다.

8. 사용자는

   - 지원사업 출처
   - 판단 근거
   - 리스크 결과
   - 다음에 확인할 행동

   을 확인한다.


# 3. MUST — 제출 MVP 핵심 기능

아래 기능은 제출 MVP에서 우선적으로 완성한다.


## M1. 사용자 유형 선택

사용자는 다음 세 유형 중 하나를 선택할 수 있다.

- 예비창업자
- 소상공인
- 프리랜서

Status:
PLANNED


## M2. 사용자 프로필 입력

지원사업 탐색에 필요한 최소 프로필을 입력한다.

현재 후보:

- 사용자 유형
- 지역
- 업종
- 자본금

실제 필드는 확보한 지원사업 데이터 Schema에 맞춰 확정한다.

Status:
PLANNED


## M3. 지원사업 데이터 조회

실제로 확보하고 검증한 공개 데이터를 Backend에서 조회한다.

대상 후보:

- 정부지원사업
- 정책자금
- 지자체 지원사업

지원사업 데이터가 확보되지 않은 상태에서
가상의 지원사업을 생성하지 않는다.

Status:
PLANNED


## M4. 사용자 조건 기반 지원사업 Matching

사용자 프로필과 지원사업의 명시적 조건을 비교한다.

명확한 조건은 LLM이 아닌
structured query 또는 deterministic logic으로 처리한다.

예:

- 지역
- 대상 유형
- 업종
- 신청 기간
- 기타 실제 Dataset에서 확인 가능한 조건

Status:
PLANNED


## M5. Match Evidence 표시

지원사업 결과에 단순 추천 점수만 표시하지 않는다.

가능한 범위에서 다음을 표시한다.

- 일치한 조건
- 추가 확인이 필요한 조건
- 정보 출처
- 기준일 또는 수집일

지원 자격을 확인할 수 없는 경우
임의로 적격 판정을 내리지 않는다.

Status:
PLANNED


## M6. 지원사업 상세 조회

사용자가 추천 또는 검색된 지원사업을 선택하면
주요 내용을 확인할 수 있다.

예:

- 사업명
- 운영기관
- 주요 지원 내용
- 주요 대상
- 신청 기간
- 출처

실제 데이터에 존재하는 항목만 표시한다.

Status:
PLANNED


## M7. 재무·창업 리스크 계산

사용자가 입력한 값을 기반으로
Backend에서 deterministic calculation을 수행한다.

현재 기획상 후보 입력:

- 초기 비용
- 매출
- 지출
- 대출 조건

현재 기획상 후보 출력:

- 자금 소진 속도
- 버틸 수 있는 기간
- 사업 악화 시 재무 상태
- 폐업 가정 시 잔존 채무

최종 계산식과 입력값은 별도 검증 후 확정한다.

LLM에게 계산을 수행시키지 않는다.

Status:
PLANNED


## M8. AI 결과 설명

생성형 AI는 Backend가 생성한

- 사용자 조건
- 지원사업 검색 결과
- Matching Evidence
- 계산 결과

를 받아 사용자에게 설명한다.

AI는 존재하지 않는 지원사업이나
금융수치를 새로 생성해서는 안 된다.

Status:
PLANNED


## M9. 출처 표시

최종 결과에서 사용자가
정보의 원출처를 확인할 수 있어야 한다.

가능하면 다음을 제공한다.

- source
- source_url
- 기준일 또는 수집일

Status:
PLANNED


## M10. Unsupported / 추가확인 처리

데이터만으로 판단하기 어려운 경우
AI가 임의로 결론을 내리지 않는다.

예:

- 추가 확인 필요
- 데이터 없음
- 현재 정보만으로 판단 불가

등의 상태를 제공한다.

Status:
PLANNED


## M11. Public Web Service

심사자가 별도 설치 없이
제출 URL에서 주요 기능을 직접 사용할 수 있어야 한다.

최소 조건:

- Public URL
- Frontend 접근 가능
- Backend 정상 연결
- 핵심 API 정상 작동
- 오류 입력 처리
- 서비스 재시작 후 정상 동작

Status:
PLANNED


# 4. SHOULD — 시간 허용 시 구현

MUST 기능이 안정적으로 작동한 이후에만 구현한다.


## S1. CSV / Excel 매출장표 업로드

소상공인의 매출장표를 업로드하여
재무 분석 입력값으로 활용한다.

단,

다양한 금융기관 포맷을 모두 지원하려 하지 않는다.

MVP에서는 사전에 정의한 Sample Schema만 지원하는 방안을 허용한다.

Status:
OPTIONAL


## S2. 프리랜서 소득 안정성 분석

기간별 소득 데이터를 기반으로
소득 변동성 및 안정성을 정량적으로 보여준다.

계산 기준이 명확히 정의된 경우에만 구현한다.

Status:
OPTIONAL


## S3. 사용자 유형별 전용 Widget

예:

- 예비창업자: 리스크 계산
- 소상공인: 매출 분석
- 프리랜서: 소득 안정성

Frontend 일정과 Backend 기능 완성도를 확인한 후 적용한다.

Status:
OPTIONAL


## S4. 지원사업 비교

두 개 이상의 지원사업을 선택해
주요 조건을 비교하는 기능.

Status:
OPTIONAL


## S5. AI Follow-up Question

최초 결과 이후 사용자가
추가 자연어 질문을 이어갈 수 있도록 한다.

핵심 Matching 및 Calculation이 완성된 뒤 구현한다.

Status:
OPTIONAL


# 5. NOT MVP — 이번 예선에서 우선 제외

다음 기능은 핵심 MVP가 완성되기 전에는 개발하지 않는다.


## N1. 실제 지원사업 신청 대행

이번 MVP에서 실제 신청 제출까지 자동화하지 않는다.


## N2. 지원서 자동 제출

정부 또는 지자체 시스템에
사용자 대신 자동 제출하지 않는다.


## N3. 실제 대출 신청

금융기관에 실제 대출 신청을 수행하지 않는다.


## N4. 대출 승인 예측 보장

사용자의 실제 대출 승인 여부를
AI가 확정적으로 예측하거나 보장하지 않는다.


## N5. 실제 신용평가 모델

금융기관 수준의 신용평가 모델을
이번 MVP 핵심 범위로 두지 않는다.


## N6. 마이데이터 직접 연동

실제 금융기관 계좌 또는
마이데이터 API 직접 연동은 우선 제외한다.


## N7. 세무사·컨설턴트 Marketplace

장기 확장 기능으로 관리한다.


## N8. B2B SaaS 기능

지자체·창업지원기관용 관리자 SaaS는
확장 방향으로만 유지한다.


## N9. 복잡한 Multi-Agent System

핵심 기능 구현에 필요성이 검증되지 않는 한 제외한다.


## N10. Graph DB

명확한 성능 또는 사용자 가치 개선이 검증되지 않는 한 제외한다.


## N11. Vector DB 전면 적용

비정형 공고문 검색에서 실제 필요성이 확인될 경우에만
일부 적용을 검토한다.


# 6. MVP Success Criteria

MVP는 단순히 화면이 존재한다고 완료로 판단하지 않는다.

다음 시나리오가 실제로 작동해야 한다.


## Scenario A — 지원사업 탐색

사용자 프로필 입력

→ Backend 요청

→ 실제 지원사업 데이터 검색

→ 사용자 조건 Matching

→ 결과 반환

→ Matching Evidence 확인

→ 원출처 확인


## Scenario B — 리스크 계산

재무 입력

→ Backend Calculation

→ 계산 결과 반환

→ 사용자 화면 표시


## Scenario C — AI 설명

검색 결과 + 계산 결과

→ LLM 입력

→ 근거 기반 설명

→ 사용자 화면 표시


# 7. Minimum Demo Quality

심사 시 다음 상태는 피한다.

- 빈 화면
- Mock UI만 존재
- 버튼이 작동하지 않음
- 검색 결과 하드코딩
- 존재하지 않는 지원사업 출력
- 계산 결과 하드코딩
- 출처 링크 없음
- LLM이 계산값을 임의 생성
- Backend와 Frontend 내용 불일치
- 특정 개발자 PC가 켜져 있어야 작동


# 8. Scope Reduction Rule

개발 일정이 부족하면 다음 순서대로 범위를 줄인다.

먼저 제거:

1. 지원사업 비교
2. Follow-up AI Chat
3. 사용자별 부가 Widget
4. Excel 업로드
5. 프리랜서 소득 안정성 상세 분석

끝까지 유지:

1. 실제 지원사업 데이터
2. 사용자 조건 Matching
3. Matching Evidence
4. 핵심 리스크 계산
5. AI 설명
6. 출처 표시
7. Public 배포


# 9. Final Submission Rule

최종 제출 전 모든 기능의 Status를 다시 검증한다.

사용 가능한 상태:

- IMPLEMENTED
- VERIFIED

미완성 상태:

- PLANNED
- IN_PROGRESS
- OPTIONAL
- FAILED

공식 기능명세서에는
IMPLEMENTED 또는 VERIFIED 상태의 기능만 작성한다.
